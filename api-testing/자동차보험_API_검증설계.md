# 화면·기간계 상태 기반 자동차보험 API 검증 설계

## 1. 문서 목적

본 문서는 [자동차보험 가입·계약변경 품질 리스크 분석 및 테스트 전략](../insurance/자동차보험_가입_프로세스_테스트_분석_및_테스트_포인트_도출.md)에서 정리한 가입·결제·계약변경의 업무 규칙과 화면 흐름을 API 검증 관점으로 재구성한 개인 실습 문서다.

사용자 화면·기간계·모니터링 로그에서 확인한 업무 흐름을 바탕으로 입력·처리·후속 반영 정보 범주와 오류 시나리오를 설계했다.

## 2. 정보 구분

| 구분 | 의미 |
| --- | --- |
| 직접 확인 | 사용자 화면·기간계·모니터링 로그에서 실제 업무 중 관찰한 동작과 상태이며, API 호출이나 필드 확인을 의미하지 않음 |
| 검증 설계 | 화면 흐름과 업무 규칙을 기준으로 도출한 입력·처리·후속 반영 정보 범주와 오류 시나리오 |
| 미확인 | 실제 API 엔드포인트·HTTP 메서드·요청 및 응답 필드·내부 구현 정보·개발 원인 |

## 3. 설계 원칙

화면 흐름을 API 검증 관점으로 재구성할 때는 단일 응답의 성공 여부뿐 아니라 `화면 입력 → 요청 정보 → 처리 상태 → 화면 반영 → 후속 업무 반영`의 일치 여부를 확인하도록 설계했다.

주요 판단 기준은 다음과 같다.

- 외부 조회 결과는 정보 항목별 성공·실패와 전체 조회 실패를 구분한다.
- 재조회 시 기존 유효정보와 새로운 결과의 반영 기준을 구분한다.
- 가입 흐름에서는 화면에서 확정한 차량·운전자·담보·특약 정보가 보험료 계산·청약내용·결제금액에 동일하게 반영되는지 확인한다.
- 계약변경 흐름에서는 변경 전후 조건이 배서내역과 환급 결과에 맞게 반영되는지 별도로 확인한다.
- 결제 승인·청약 완료·계약 생성·가입 완료의 단계별 처리 결과를 구분한다.

## 4. 업무 흐름별 검증 정보

다음 표는 화면에서 확인한 입력·조건을 기준으로 처리 결과와 후속 업무에서 확인할 정보 범주를 정리한 것이다.

| 업무 흐름 | 화면에서 확인한 입력·조건 | 처리 결과에서 확인할 정보 | 후속 반영 |
| --- | --- | --- | --- |
| 차량 기본조회 | 차량번호 | 조회 성공·실패 상태, 차명·연식·연료방식 | 조회된 차량정보를 자동차 상세정보 선택에 반영 |
| 출고 부속정보 조회 | 조회 대상 차량번호 | 할인부속·기타부속의 부속명·설치금액·현재가액·적용 여부 | 최종 부속정보와 총차량가액을 보험료 계산에 반영 |
| 제조사 차량데이터 조회 | 조회 대상 차량정보·정보처리 동의 상태 | 내장형 영상기록장치·첨단안전장치 장착 여부·제조사 연계 서비스 이용 상태·할인특약 적용 가능 여부·주행거리 조회 상태 | 조회 결과를 할인특약·주행거리 특약 처리와 보험료 계산에 반영 |
| 운전자 조건 | 운전자 범위·생년월일·관계·연령 조건 | 입력 유효성·가입 제한·적용 가능한 할인특약 | 확정된 운전자 조건과 할인특약을 보험료 계산에 반영 |
| 보험료 계산 | 차량·운전자·담보·가입금액·할인특약 | 담보별 보험료·할인 결과·최종보험료·계산 상태 | 최종보험료를 청약내용과 결제금액에 반영 |
| 보험료 결제 | 결제수단·결제금액·동의·본인인증 결과 | 결제 승인 여부·청약 상태·계약 생성 여부·가입 완료 상태 | 가입 완료 화면과 후속 안내에 반영 |
| 안전운전 할인특약 배서 | 기존 계약정보·조회점수·변경 기준일·환급정보 | 추가 할인 가능 여부·변경 전후 점수·할인구간·환급보험료·배서·환급 상태 | 배서내역·환급 결과·완료 안내에 반영 |

### 공통 검증 기준

| 정보 범주 | 검증 관점 |
| --- | --- |
| 계약 식별·상태정보 | 식별정보 누락, 조회 계약 불일치와 자동차보험 계약 상태에 따른 요청 허용 여부 |
| 정보처리 동의 | 미동의 상태에서 외부 데이터 조회가 실행되지 않는지 확인하고, 미동의 상태와 조회 실패를 구분 |
| 보험료·결제금액 | 저장된 최종보험료·청약내용·결제금액·기간계 보험료의 일치 여부 |
| 처리 상태 | 청약 완료·결제 승인·계약 생성·가입 완료가 정상 순서로 이어지는지 확인하고, 중간 실패가 가입 완료로 표시되지 않는지 구분 |

## 5. 핵심 검증 시나리오

다음 시나리오는 실제 업무에서 확인한 화면 흐름과 기대 동작을 API 검증 관점으로 재구성했다.

| 업무 흐름 | 조건 | 기대 결과 | 주요 위험 |
| --- | --- | --- | --- |
| 차량 부속정보 | 기존 입력 할인부속과 외부 조회된 동일 할인부속이 존재 | 외부 조회 할인부속을 우선 반영하고 동일 부속은 하나만 유지하며, 중복되지 않은 기존 유효정보는 보존 | 부속 중복·총차량가액 이중 반영 |
| 제조사 차량데이터 조회 | 커넥티드 주행거리 조회 실패 | 커넥티드 마일리지 특약을 해제하고 사진형으로 전환하며 사진등록 화면을 즉시 표시 | 사진등록 단계 누락·미등록 상태로 후속 단계 진행 |
| 보험료 계산 | 계산 중단 후 이전 단계 이동·재진입 | 기존 저장 조건을 유지하고 재진입 시 현재 조건으로 보험료를 다시 계산 | 변경 전 보험료 잔존·현재 조건 미반영 |
| 보험료 결제 | 간편결제 후 보험사 화면 복귀 시 결과 반영 지연 | 청약정보를 유지하고 최종 결제·계약 상태를 확인한 후 가입 완료 여부를 표시 | 가입 결과 오인·불필요한 재결제 시도 |
| 안전운전 할인특약 배서 | 기존 계약에서 점수를 재조회해 추가 할인 대상 확인 | 변경 점수·할인율·환급보험료를 일치시키고 배서·환급 상태에 반영 | 할인율·환급보험료·배서상태 불일치 |

실제 API 테스트 환경이 제공되는 경우, 요청·응답 결과와 화면 반영값·후속 업무 반영값·기간계 최종 상태의 일치 여부를 판정 기준으로 사용하도록 설계했다.

---

## 6. 확인 한계

- 실제 API 명세와 테스트 환경이 없어 요청·응답 필드를 검증하지 않았다.
- DB에 접근해 저장 데이터와 화면 결과를 비교하지 않았다.
- 실제 타임아웃·재시도 정책과 외부기관별 오류코드는 확인하지 않았다.
