# 자동차보험 API 검증설계

## 1. 문서 개요

본 문서는 자동차보험 가입·결제·계약변경 화면에서 확인할 수 있는 입력값과 상태 변화를 기준으로 API 검증 관점을 설계한 개인 실습 문서다.

직장에서 실제 보험사의 API를 직접 실행한 결과가 아니며, 실제 엔드포인트·HTTP 메서드·요청 및 응답 스키마·내부 시스템 구조는 사용하지 않았다.

화면에서 직접 확인한 값과 API 요청·결과 후보를 구분하고, 실행하지 않은 테스트 결과는 작성하지 않는다.

## 2. 작성 구분

| 구분 | 의미 |
| --- | --- |
| 직접 확인 | 화면·기간계·모니터링 화면에서 직접 확인한 동작과 상태 |
| 검증 후보 | 화면 흐름을 기준으로 도출한 요청정보·결과정보·상태 검증 관점 |
| 미확인 | 실제 엔드포인트·필드명·HTTP 상태코드·DB 구조·개발 원인 |

## 3. 공통 분석 구조

각 영역은 다음 순서로 분석한다.

> 화면 입력·동작 → 요청 발생 지점 후보 → 요청정보 범주 후보 → 처리 결과 후보 → 화면 반영 → 다음 단계 전달 → 실패·재시도 → 업무 영향

세부차종을 변경해도 기존 부속정보는 유지되고, 변경된 차량가액과 기존 부속정보를 기준으로 총차량가액이 다시 계산되는 업무규칙을 검증 대상으로 포함한다.

| 동의 미완료 | 제조사 조회만 제한하고 자동차보험 가입은 계속 진행 |
| 조회 성공 | 특약별 가입 가능 여부와 결과를 화면에 반영 |

| 부분 조회 | 특약정보는 반영하고 주행거리 결과만 사진형 방식으로 대체 |
| 전체 실패 | 실패 안내 후 팝업 종료, 재조회 가능 |
| 모니터링 | 조회 수행 기록과 성공·실패 결과 확인 |
| 미확인 | 실제 호출 횟수·응답 필드·구체적인 실패 원인 |

특약정보 조회 성공·주행거리 결과 없음과 전체 조회 실패를 서로 다른 상태로 구분한다.

## 5. 운전자 조건

### 5.1 대표 검증 범위

전체 운전자 범위를 나열하지 않고 입력정보와 업무규칙이 구분되는 대표 조건 5개를 대상으로 설계한다.

| 운전자 범위 | 입력정보 | 주요 검증 |
| --- | --- | --- |
| 기명피보험자 1인 | 추가 입력 없음 | 기명피보험자 기준 적용 |
| 부부 한정 | 배우자 생년월일 | 피보험자와 배우자 정보 구분 |
| 가족 한정 | 최저연령 운전자의 생년월일·관계 | 최저연령과 관계 조건 반영 |
| 누구나 | 연령 한정 | 선택 연령 기준 반영 |
| 자녀 한정 | 생년월일·관계 | 기명피보험자 운전 제한·할인특약 가입 조건 |

### 5.2 운전자 조건 확정

| 분석 항목 | 내용 |
| --- | --- |
| 요청 발생 지점 | 운전자 범위와 조건 입력 후 다음 선택 |
| 요청정보 후보 | 운전자 범위·생년월일·관계·연령 조건 |
| 결과정보 후보 | 입력 유효성·가입 제한 안내·적용 가능한 할인특약 |
| 부부 한정 검증 | 피보험자와 배우자 정보의 동일·유사 입력 확인 |
| 자녀 한정 검증 | 기명피보험자 운전 제한과 가입 불가 특약 안내 |
| 특약 가입 불가 범위 | 해당 할인특약 미노출 |
| 가입 가능 범위로 복귀 | 기존 조회 결과와 가입상태 복원 |
| 할인율 구간 변경 | 변경한 운전자 범위 기준으로 할인율 재적용 |
| 다음 단계 | 보험료 계산결과 |
| 최종 확인 | 청약내용 확인 화면에서 운전자 조건 비교 |

화면에서 미노출된 할인특약 정보가 삭제된 것인지 임시로 유지된 것인지 구분하고, 가입 가능한 운전자 범위로 복귀했을 때 기존 조회 결과와 가입상태가 복원되는지 검증한다.

## 6. 보험료 계산

| 분석 항목 | 내용 |
| --- | --- |
| 요청 발생 지점 | 운전자정보 단계에서 다음 선택·담보 또는 특약 변경 후 저장 |
| 요청정보 후보 | 차량조건·운전자 조건·담보·가입금액·할인특약 |
| 결과정보 후보 | 담보별 보험료·할인특약 적용 결과·최종보험료 |
| 최초 계산 | 보험료 계산결과 화면 진입 시 자동 계산 |
| 변경 중 상태 | 담보·특약 변경에 따른 임시 보험료 표시 |
| 최종 확정 | 변경내용 저장 후 최종보험료 확정 |
| 저장 후 상태 | 최종보험료 확정 후 버튼이 다음 단계 이동으로 변경 |
| 화면 표시 | 담보명·담보한도·담보별 보험료·할인특약·최종보험료 |
| 비교값 | 마일리지 할인 전·후 보험료·전년도 계약 보험료 |
| 재진입 | 이전 단계에서 변경된 최종 조건으로 보험료 재계산 |
| 계산 지연·실패 | 로딩 상태가 유지되고 다음 단계로 이동하지 못함 |
| 복구 | 이전 단계로 이동한 후 보험료 계산결과에 재진입해 다시 계산 |
| 실패 시 데이터 | 변경내용 저장 전 보험료 유지 |
| 다음 단계 | 피보험자·계약자정보 및 청약내용 확인 |
| 주요 위험 | 임시값과 최종값 불일치·할인특약 미반영·이전 보험료 잔존 |

운전자 범위 변경으로 할인특약이 미노출되면 할인 미적용 보험료가 계산돼야 하며, 다시 가입 가능한 범위로 복귀하면 특약과 할인보험료가 재적용돼야 한다.

로딩 중 반복 입력으로 실제 요청이 중복됐는지는 확인하지 못했다. 개인 설계에서는 로딩 중 반복 입력을 제한하고 하나의 최종 계산 결과만 반영되는지를 검증한다.

## 7. 결제·계약 생성

| 분석 항목 | 내용 |
| --- | --- |
| 요청 발생 지점 | 결제정보 입력·계약체결 동의 후 결제 요청 |
| 요청정보 후보 | 청약 식별정보·결제수단·결제금액·동의 및 인증 결과 |
| 결과정보 후보 | 승인상태·청약상태·계약 생성 결과 |
| 성공 흐름 | 본인인증·승인·계약 생성·가입 완료 |
| 직접 확인 | 결제승인상태·청약상태·계약번호·기간계 계약·가입 완료 화면 |
| 후속 결과 | 알림톡·문자·증권 발송·모니터링 기록 |
| 실패·미완료 | 계약 미생성·가입 완료 미표시·알림 미발송 |
| 데이터 유지 | 결제 실패·미완료 후 청약정보 유지 |
| 결과 반영 지연 | 결제 승인과 계약 생성은 완료됐지만 가입 완료 화면은 로딩 상태 유지 |
| 다음 단계 | 가입 완료 |
| 주요 위험 | 결제와 계약 상태 불일치·결제 승인 후 계약 미생성·화면 결과 반영 지연 |

결제 성공 여부만 확인하지 않고 청약상태·계약 생성·가입 완료·후속 안내 결과가 동일한 상태를 나타내는지 검증한다.

결제 승인과 계약 생성이 완료됐지만 화면 반영이 늦어지는 상태를 구분하고, 화면 로딩 중 최종 처리상태를 확인할 수 있는지를 검증한다.

## 8. 안전운전 할인특약 배서

### 8.1 환급보험료 발생

| 분석 항목 | 내용 |
| --- | --- |
| 사전조건 | 최대 할인율보다 낮은 할인율로 가입된 기존 계약 |
| 요청 발생 지점 | 안전운전 점수 재조회 |
| 요청정보 후보 | 기존 계약정보·조회 점수·변경 기준일 |
| 결과정보 후보 | 변경 전·후 점수·할인구간·차액 환급보험료 |
| 처리 흐름 | 점수 재조회·차액 계산·배서 확인·환급정보 입력·배서 완료 |
| 직접 비교 | 변경 전·후 점수·변경 기준일·웹·모바일·기간계 금액 |
| 완료 확인 | 배서 청약번호·특약정보·환급상태·배서내역 |
| 후속 결과 | 알림톡·문자·이메일 |
| 주요 위험 | 채널별 환급보험료 불일치·환급정보 미반영·배서상태 불일치 |

### 8.2 동일 할인구간

| 상태 | 기대결과 |
| --- | --- |
| 점수 변경·할인구간 동일 | 환급보험료 0원 |
| 다음 선택 | 환급금 미발생 안내 |
| 후속 처리 | 환급정보 입력 단계로 진행하지 않음 |
| 배서 결과 | 배서 청약 및 배서계약을 생성하지 않음 |

동일 할인구간과 할인구간 변경을 분리해 불필요한 0원 배서가 생성되지 않는지 검증한다.

### 8.3 성공 후 재조회 실패

| 상태 | 기대결과 |
| --- | --- |
| 첫 번째 조회 성공 | 유효 점수와 할인율 반영 |
| 두 번째 조회 실패 | 조회 실패 안내 표시 |
| 유효 결과 유지 | 이전 성공 점수와 해당 점수 구간의 할인율 유지 |
| 특약 상태 | 기존 특약 가입상태 유지 |
| 후속 처리 | 유지된 유효 결과로 가입 진행 가능 |
| 모니터링 | 성공 조회와 실패 조회를 각각 구분해 기록 |

재조회 실패가 이전의 유효한 성공 결과를 덮어쓰지 않는지를 확인한다. 이전 성공 결과가 없는 최초 조회 실패 조건은 직접 확인하지 못했으므로 별도 검증 후보로 구분한다.

| 출고 부속조회 | 부속명·설치금액·현재가액·적용 여부 | 총차량가액·보험료 계산 | 중복·이전값·가액 이중 반영 방지 |
| 제조사 데이터 조회 | 장착·서비스 상태·특약 가입 가능 여부·주행거리 결과 | 할인특약·마일리지 처리 | 전체 실패와 부분 조회 구분 |
| 운전자 조건 | 운전자 범위·최저연령·관계 | 할인특약·보험료 계산 | 가입 가능 특약·할인율 재적용 |

| 결제 | 결제금액·승인상태·청약상태 | 계약 생성 | 승인·청약·계약상태 일치 |
| 계약 생성 | 계약번호·계약상태 | 가입 완료·증권·안내 | 계약 생성 이후에만 완료 처리 |
| 안전운전 배서 | 변경 점수·기준일·환급보험료·환급정보 | 배서계약·환급·안내 | 배서·환급·채널별 금액 일치 |

단계별 요청 횟수와 내부 호출 순서는 확인하지 않았다. 각 화면에서 확인한 최종 입력과 결과가 다음 단계에 일관되게 반영되는지를 검증한다.

## 10. 실패·복구 검증

### 10.1 직접 확인한 상태

| 영역 | 실패·지연 상태 | 복구 방식 | 데이터 상태 |
| --- | --- | --- | --- |
| 차량 기본조회 | 별도 안내 없이 수기 선택 화면 제공 | 제조사부터 직접 선택 | 실패 원인 미확인 |
| 출고 부속조회 | 조회 실패 | 부속정보 직접 입력 | 재진입 후 직접 입력값 유지 |
| 제조사 데이터 조회 | 조회 실패 | 정보처리 동의부터 다시 진행해 재조회 | 새로운 성공 또는 실패 결과 표시 |
| 보험료 계산 | 로딩 상태에서 정지·다음 단계 이동 불가 | 이전 단계 이동 후 재진입 | 저장 전 보험료 유지·재진입 시 재계산 |
| 간편결제 | 보험사 화면 복귀 후 결과 반영 지연 | 로딩 후 최종 상태 반영 | 결제 승인·계약 생성 완료·청약정보 유지 |
| 안전운전 점수 조회 | 이전 성공 후 재조회 실패 | 실패 안내 후 팝업 종료 | 이전 성공 점수·할인율·특약 가입상태 유지 |

차량 기본조회 결과가 없는 상태는 무응답·타임아웃·조회 대상 없음 중 어떤 원인인지 화면만으로 구분할 수 없었다.

### 10.2 개인 설계 검증 후보

- 조회 결과 없음과 통신 실패를 서로 다른 상태로 구분한다.
- 재조회 시 이전 실패 결과가 새로운 성공 결과를 덮어쓰지 않는지 확인한다.
- 부분 성공한 데이터는 유지하고 실패한 항목만 대체 흐름으로 전환한다.
- 로딩 중 반복 입력을 제한하고 하나의 최종 결과만 반영되는지 확인한다.
- 화면 결과 반영이 지연될 때 이미 완료된 결제·계약 상태를 다시 확인할 수 있는지 검증한다.
- 최초 조회 실패와 이전 성공 후 재조회 실패의 데이터 유지 기준을 구분한다.

실제 타임아웃 시간·API 재시도 횟수·중복 요청 처리 방식은 확인하지 않았다.

## 11. 모니터링 확인 관점

### 11.1 직접 확인한 모니터링 정보

| 구분 | 확인 항목 | 검증 활용 |
| --- | --- | --- |
| 화면 흐름 기록 | 발생순서·발생시각·업무단계·상세동작·채널·페이지·업무 연계 식별정보 | 고객 진행 경로와 마지막 정상 동작 확인 |
| 오류 상세 기록 | 오류 발생시각·오류 식별값·오류내용·오류유형·오류구분·발생채널·업무 연계 식별정보 | 화면 중단 시점과 오류 기록 연결 |
| 보험료 계산 흐름 | 보험료 계산 진입·변경·완료·안내 기록 | 보험료 계산 전후 화면 흐름 비교 |
| 결제 흐름 | 외부 결제 요청·승인·미완료·청약·계약 상태 | 결제 결과와 계약 생성 여부 비교 |
| 안전운전 배서 | 점수·조회 성공/실패·실패 사유·환급보험료·환급배서 청약정보 | 점수 조회와 배서·환급 결과 연결 |

화면 흐름 기록과 오류 상세 기록의 발생시각·업무단계·채널·업무 연계 식별정보를 비교해 오류가 발생한 구간을 확인한다.

여러 번 수행한 작업은 각각 별도 기록으로 쌓이는 결과를 확인했으며, 하나의 요청에 대한 재시도 횟수 필드는 확인하지 못했다.

오류 식별값과 오류유형을 통해 기간계 처리 오류와 화면 또는 서비스에서 정의한 오류를 구분해 확인한 경험이 있다. 실제 오류코드 값과 내부 정의는 공개하지 않는다.

### 11.2 개인 설계상 추가로 필요한 정보

- 요청 발생 여부
- 외부조회 결과 수신 여부
- 처리 성공·실패 상태
- 오류 발생 구간
- 재시도 여부와 횟수
- 처리시간
- 결제·청약·계약·증권 상태
- 반복 요청을 구분할 수 있는 거래 식별정보

위 항목은 실제 API 모니터링 화면에서 직접 확인한 결과가 아니라, 장애 분석과 상태 정합성 확인을 위해 필요한 검증 후보다.

### 11.3 공개 제외 정보

- 고객·계약·차량 식별정보
- 청약·세션 식별값의 실제 값
- 내부 오류코드와 오류메시지 원문
- 내부 URL·페이지 경로·시스템 구조
- 실제 모니터링 화면 캡처

## 12. 완료 기준과 잔존 위험

### 12.1 설계 완료 기준

- 차량·운전자·보험료·결제·배서의 데이터 흐름을 연결했다.
- 화면에서 직접 확인한 값과 요청·결과 후보를 구분했다.
- 성공·실패·부분 성공·재조회 상태를 구분했다.
- 보험료·결제·계약·배서 상태의 정합성 검증 관점을 작성했다.
- 실제 모니터링 경험과 개인 설계상 필요한 항목을 구분했다.
- 실제 경험으로 오인될 Endpoint·Payload·HTTP 상태코드·실행 결과를 작성하지 않았다.

### 12.2 잔존 위험

- 실제 API 명세와 테스트 환경이 없어 요청·응답 필드를 검증하지 못했다.
- DB 접근 권한이 없어 저장 데이터와 화면 결과를 직접 비교하지 못했다.
- 성능·부하·동시성 테스트를 수행하지 않았다.
- 실제 네트워크 타임아웃과 재시도 정책을 확인하지 못했다.
- 반복 요청을 구분하는 실제 거래 식별정보를 확인하지 못했다.
- 외부기관별 상세 오류코드와 복구 정책을 확인하지 못했다.
- API 자동화와 UI 자동화를 구현하지 않았다.

## 13. 확인 한계

- 실제 API 엔드포인트와 요청·응답 스키마를 확인하지 않았다.
- HTTP 상태코드와 내부 오류코드를 실제 결과처럼 작성하지 않았다.
- DB와 내부 시스템 간 연계 구조를 확인하지 않았다.
- 요청·응답 후보는 화면과 업무 상태를 기준으로 설계했다.
- 본 문서는 API 테스트 실행 결과가 아닌 개인 검증설계다.
