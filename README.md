# Insurance QA Career Project 2026

보험 고객상담 및 다이렉트 업무지원 과정에서 쌓은 도메인 경험과 테스트 참여 경험을 바탕으로 작성한 보험·핀테크 QA 포트폴리오다.

자동차보험 가입·갱신·계약변경 과정의 업무규칙을 분석하고, 실제 업무에서 확인한 오류와 수정 후 재검증 범위를 테스트케이스와 결함 보고서로 정리했다.

API 검증설계와 보험 상담 LLM QA는 직장에서 수행한 실무 경험이 아닌 개인 실습으로 구분했다.

공식 QA 직무로 수행하지 않은 경험을 QA 경력으로 과장하지 않았으며, 직접 확인한 범위와 확인하지 못한 범위를 문서에 명시했다.

---

## 프로젝트 핵심 범위

- 자동차보험 가입·갱신·계약변경 업무규칙 분석
- 외부 조회정보와 기존 계약정보의 데이터 정합성 검증
- PC·모바일·기간계 결과 비교
- 보험료 계산부터 결제·가입 완료까지 후속 흐름 확인
- 고객 문의와 운영 오류의 재현 조건 확인
- 오류 전달 및 수정 후 회귀검증
- 화면과 업무 흐름을 기반으로 한 API 검증설계
- 공개 보험 상담 AI 서비스의 응답 품질 검증

## 핵심 산출물

### 1. 자동차보험 프로세스 분석

[자동차보험 가입 프로세스 테스트 분석 및 테스트 포인트 도출](./insurance/자동차보험_가입_프로세스_테스트_분석_및_테스트_포인트_도출.md)

자동차보험 가입 과정을 고객정보부터 보험료 결제와 가입 완료까지 구분하고, 화면별 입력값·처리 동작·데이터 전달·오류 처리 및 업무 영향을 정리했다.

주요 분석 범위는 다음과 같다.

- 차량상세정보
- 운전자 범위
- 보험료 계산 결과
- 보험료 결제
- 운전점수 할인특약 계약변경
- 외부 차량정보 조회
- 조회 실패와 재시도
- 화면·기간계 데이터 정합성

### 2. 핵심 테스트케이스

[자동차보험 핵심 테스트케이스](./test-cases/자동차보험_핵심_테스트케이스.md)

일반적인 필수값 검증보다 보험 업무규칙, 외부 연동, 데이터 유지 및 채널 간 정합성을 보여주는 핵심 사례 4건을 수록했다.

| TC ID | 영역 | 테스트 주제 |
| --- | --- | --- |
| VEH-002 | 차량정보 | 외부조회 부속과 기존 입력 부속의 중복 처리 |
| PRM-002 | 보험료 | 내장형 영상기록장치 자동 승계 시 할인율 정합성 |
| EVD-001 | 외부연동 | 외부 주행거리 조회 실패 후 사진형 정산 전환 |
| REN-001 | 갱신 | 계약변경 후 반려동물 등록정보 유지 |

### 3. 결함 보고서

[자동차보험 결함 보고서](./bug-reports/README.md)

실제 업무에서 확인한 오류 중 재현 조건, 기대결과와 실제결과 및 업무 영향을 별도로 보여줄 필요가 있는 대표 사례를 정리했다.

- [BUG-001 갱신가입 차량부속정보 중복오류](./bug-reports/BUG-001_갱신가입_차량부속정보_중복오류.md)
- [BUG-002 보험 효력 개시 전 계약에서 실시간 단기운전자 특약 가입 가능 오류](./bug-reports/BUG-002_보험_효력_개시_전_계약에서_실시간_단기운전자_특약_가입_가능_오류.md)

테스트케이스와 결함 보고서는 일대일로 구성하지 않았다.

`BUG-001`은 `VEH-002`와 같은 사례이며, `BUG-002`는 핵심 테스트케이스 4건에 포함하지 않고 별도의 대표 결함 보고서로 유지했다.

### 4. API 검증설계 — 개인 실습

[자동차보험 API 검증설계](./api-testing/자동차보험_API_검증설계.md)

자동차보험 가입·결제·계약변경 화면에서 확인할 수 있는 입력값과 상태 변화를 기준으로 API 검증 관점을 설계했다.

주요 검증설계 범위는 다음과 같다.

- 차량 기본정보와 출고 차량 부속정보 조회
- 제조사 차량데이터 조회와 동의 상태
- 운전자 조건과 할인특약 적용
- 보험료 계산과 변경값 반영
- 결제 승인과 계약 생성 상태
- 안전운전 할인특약 계약변경과 환급 상태
- 조회 실패·재시도·이전값 유지
- 화면·기간계·모니터링 정보의 상태 정합성

직장에서 실제 보험사의 API를 직접 실행한 결과가 아니며, 실제 엔드포인트·HTTP 메서드·요청 및 응답 스키마·내부 시스템 구조는 사용하지 않았다.

화면에서 직접 확인한 동작은 `직접 확인`, 화면 흐름에서 도출한 요청정보와 결과정보는 `검증 후보`, 확인하지 못한 내부 정보는 `미확인`으로 구분했다.

### 5. 보험 상담 LLM QA — 개인 실습

[보험 상담 LLM QA](./llm-qa/README.md)

공개 보험 상담 AI 서비스 1종을 대상으로 평가기준과 테스트케이스를 설계하고, 단기운전자 특약 관련 대표 시나리오 7건을 실행했다.

#### 세부 문서

- [보험상담 LLM 응답품질 평가기준](./llm-qa/보험상담_LLM_응답품질_평가기준.md)
- [보험상담 LLM 테스트케이스](./llm-qa/보험상담_LLM_테스트케이스.md)
- [단기운전자 특약 조건변경·계약정보 미확인 상황 LLM 응답 검증](./llm-qa/단기운전자_특약_조건변경_LLM_응답_검증.md)

주요 검증 영역은 다음과 같다.

- 정보가 부족한 상황의 추가 확인
- 운전자 범위·연령 조건 확인
- 조건변경에 따른 기존 판단 수정
- 당일 운전과 특약 효력시점
- 자동차보험과 운전자보험의 출처 구분
- 개인정보 보호와 계약조회 권한
- 자동차보험 만기일을 넘는 특약기간
- 보험사별 최대 가입기간과 연속·중복 가입
- 확인된 정보와 일반 보험정보의 구분

2026년 7월 29일 실행한 대표 시나리오 7건의 판정은 다음과 같다.

- `PASS`: 0건
- `CONDITIONAL PASS`: 2건
- `FAIL`: 5건
- 합계: `0 + 2 + 5 = 7건`

이 결과는 선정한 시나리오 7건에서 관찰한 결과이며, 해당 AI 서비스 전체의 오류율이나 품질 수준을 의미하지 않는다.

실제 직장에서 수행한 LLM QA 경험이 아니며, 서비스의 내부 프롬프트·검색 구조·데이터베이스·개발 원인은 확인하지 않았다.

## 작성 원칙

- 특정 보험사의 내부 명칭, 실제 고객정보, 실제 보험료 및 외부업체명은 공개하지 않는다.
- 실제 업무 경험과 포트폴리오용 개인 실습을 구분한다.
- 직접 확인하지 않은 개발 원인과 내부 시스템 구조는 추측하지 않는다.
- 정상 업무규칙, 실제 오류 및 수정 후 재검증 범위를 구분한다.
- 실제 수행한 테스트와 확인 범위까지만 작성한다.
- 실행하지 않은 API 테스트를 완료 결과처럼 작성하지 않는다.
- 면접에서 발생 조건과 자신의 역할을 설명하기 어려운 사례는 제외한다.
- 수치화되지 않은 개선 효과와 확인되지 않은 결과는 작성하지 않는다.
- 특정 서비스에서 관찰한 LLM 응답 결과를 전체 서비스의 품질로 일반화하지 않는다.
